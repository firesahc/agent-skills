# 现有软件项目修改指导规范

## 一、定位与核心目标

本技能用于指导 AI 修改**已经存在的软件项目**。它不是单纯的架构设计指南，也不是只用于判断类和模块是否应该拆分的规则集。它覆盖从理解需求到验证结果的完整工程过程：

1. 明确用户希望改变什么，以及哪些行为和约束必须保留；
2. 调查现有项目中相关代码、调用关系、状态、数据流和运行机制；
3. 对问题修复或性能问题，识别现象、原因和证据；
4. 评估修改对调用方、数据、接口、运行时行为和环境的影响；
5. 比较可行方案，选择符合项目实际情况的修改方式；
6. 在明确边界内实施修改，并处理必要的兼容与失败路径；
7. 验证目标行为和回归行为，准确说明证据、限制与剩余风险。

本技能不预先规定必须复用、扩展、拆分、新增或重构。它约束的是**决策过程和修改质量**，不是预先规定决策结果。

### 核心原则

- **先理解需求，再调查代码；先理解问题，再决定改哪里。**
- **解决真实问题，不以代码改动量、文件数量或架构形式作为目标。**
- **保护不属于本次范围的既有正确行为，但不把已确认的缺陷当成必须保留的契约。**
- **让职责、状态、数据流和运行约束决定结构，而不是让现有文件布局或设计模式决定结构。**
- **控制无关变化，不人为压缩必要变化。**
- **整体评估复杂度，不把复杂度转移给其他模块、调用者或运行时协调机制。**
- **用证据说明修改结果，不把推理、代码审查、静态检查或编译通过冒充为运行验证。**

### 执行速览

每次项目修改按实际风险走完以下决策链；简单任务可以缩短分析，但不能跳过与修改直接相关的关键检查。

1. **需求边界：** 要改变什么、必须保留什么、哪些行为允许变化、如何验收？
2. **现状调查：** 相关代码、调用链、状态与数据流、依赖、生命周期和副作用是什么？
3. **问题诊断：** 当前是需求实现、局部缺陷还是结构性问题？根因有哪些证据，哪些仍是假设？
4. **影响评估：** 会影响哪些调用者、数据消费者、接口、持久化数据、平台和运行路径？
5. **方案选择：** 局部修复、复用、扩展、内部整理、新增、拆分或重构，哪一种整体成本和风险更合理？
6. **专项约束：** 根据实际变更叠加对应规则，区分硬性门槛（G）、必须检查项（C）和验收条件（A）。
7. **实施与验证：** 控制为最小完整变更，建立适用的实施前基线，验证目标行为和回归行为，并说明证据等级及剩余风险。

速览只用于定位流程，不替代后续章节中的详细约束。职责拆分仍须单独通过五项 AND 硬性门槛。

## 二、适用范围与分析深度

本技能适用于代码、架构、配置、数据、接口、依赖、构建、部署和运行方式的修改。分析深度应与修改的影响和风险匹配，不要求每项小改动都进行完整架构评审。

### 1. 简单局部修改

例如明确的拼写或变量错误、单一条件修复、简单文案调整，以及不改变职责、状态、接口或行为边界的小改动。确认目标和必要上下文后即可实施，并执行与改动相匹配的检查。不要为了形式扫描整个项目或制作复杂方案比较。

### 2. 中等复杂度修改

涉及多个方法或类、状态流转、公共调用点、文件或数据库操作、异常处理、模块间协作时，应分析相关调用链、行为边界和变更影响，并触发对应专项规则。

### 3. 高风险或高架构影响修改

涉及核心状态、持久化格式、公共接口、跨进程通信、并发、线程模型、服务生命周期、关键数据流、权限或安全边界时，应进行完整的影响分析、候选方案比较和分层验证。

**不要仅根据改动行数判断风险。** 一行代码也可能改变事务边界、权限判断、状态发布顺序或并发语义。

# 第一部分：所有项目修改都应遵循的流程

## 三、理解需求与修改边界

在分析实现方式之前，先明确用户希望系统发生什么变化。

| 维度 | 需要明确的内容 |
|---|---|
| 修改目标 | 用户希望解决的实际问题或实现的能力 |
| 目标行为 | 修改后系统应该如何表现 |
| 保留行为 | 哪些已有功能、接口和行为不能受到影响 |
| 允许变化 | 哪些现有行为正是本次需要修复或调整的对象 |
| 约束条件 | 性能、兼容性、权限、资源、平台、依赖或发布限制 |
| 验收标准 | 通过什么现象、测试或证据判断修改完成 |
| 修改范围 | 哪些内容属于本次任务，哪些属于无关改进 |

还应区分：

- 用户描述的是问题和目标，还是已经指定了实现方案；
- 用户是否要求只分析、只评审，还是允许直接修改；
- 用户提出的方案是必须遵守的约束，还是供评估的设想；
- 是否存在必须保持的接口、数据格式、兼容性或发布约束。

不要把用户提出的实现设想自动当成唯一正确方案。先理解其目的，再判断实现是否合理。用户明确指定的约束应予遵守；如果约束与正确性、安全性或其他明确要求冲突，应指出冲突，不要暗中忽略。

需求存在不确定性时，先利用代码、测试、文档和项目约定消除能够自行查明的不确定性。仍无法确定且会实质影响实现时，标记假设或提出最必要的问题。不得把未经确认的假设描述成用户要求。

## 四、理解现有系统

对可能影响系统行为或结构的修改，先调查足以解释受影响路径的上下文，不要立即从报错行或最方便修改的类开始编码。

按任务需要检查：

- 相关模块、类、接口、方法和真实职责；
- 上游调用者、下游消费者及完整调用链；
- 关键数据的来源、流向、转换和持久化位置；
- 状态的权威持有者、读取者、修改者及派生副本；
- 线程、进程、异步任务和同步机制；
- 对象、服务、组件和资源的生命周期；
- 文件、数据库、网络、系统 API、事件和回调等副作用；
- 错误处理、重试、超时、取消、恢复和资源释放；
- 日志、指标、诊断方式及现有测试；
- 构建变体、依赖版本、运行环境和平台限制。

重点回答：

1. 当前代码为什么这样组织？
2. 哪些是业务或运行时必须遵守的约束？
3. 哪些只是历史实现或偶然形成的结构？
4. 本次修改涉及的真实边界在哪里？

分析范围应覆盖所有可能受本次修改影响的路径，但不要无目的地扫描无关代码。若项目存在架构文档、设计决策记录、测试和历史实现，应结合实际代码核对，不能只相信文档或注释。

## 五、诊断问题根因

对于 Bug、异常行为、性能问题和稳定性问题，不能把表面现象直接当成根因。

```text
观察到的问题现象
    ↓
明确触发条件、时间和环境
    ↓
沿调用链追踪数据、状态和副作用
    ↓
定位第一个偏离预期的位置
    ↓
区分直接原因、根本原因和伴随现象
    ↓
使用代码、日志、测试或运行证据验证
    ↓
确定修复范围和目标行为
```

要求：

- 追踪问题发生前后的状态变化，而不只检查最终失败位置；
- 区分原因、相关性和时间上的先后关系；
- 检查异常路径、重试路径、并发路径及恢复路径；
- 不要用增加重试、吞掉异常、放宽条件或增加特殊分支掩盖尚未查明的根因；
- 不要仅凭代码形态推断实际运行行为，涉及并发、异步、系统 API 或跨进程行为时，应尽量结合运行证据；
- 证据不足时，将结论标记为假设或待验证项，不得写成已确认事实。

无法在当前环境复现问题，不代表问题不存在，也不代表可以随意推定根因。应说明已检查的路径、仍然存在的不确定性，以及能够进行的替代验证。

## 六、定义行为契约：哪些改变，哪些保持

项目修改不等于纯重构。不能机械要求所有既有行为都保持不变，也不能因为目标行为发生变化就忽略回归影响。

修改前应区分：

1. **本次需要改变的行为**：例如已确认的 Bug、被替换的业务规则或明确调整的接口语义；
2. **本次必须保持的行为**：不属于需求范围的正确功能、稳定接口、数据格式和外部约定；
3. **允许变化但必须说明的行为**：例如性能优化改变内部执行方式、接口迁移改变调用方式；
4. **未知或未确认的行为**：不能擅自认定为必须保持或允许改变，应进一步调查或明确标注。

| 修改类型 | 行为要求 |
|---|---|
| Bug 修复 | 改变错误行为，保留相关正确行为 |
| 功能新增 | 增加目标能力，不破坏无关的既有功能 |
| 功能调整 | 只改变需求明确指定的行为及必要影响范围 |
| 性能优化 | 在既定精度和语义约束下保持功能结果，允许内部执行方式变化 |
| 纯重构 | 对外可观察行为原则上保持等价 |
| 接口升级 | 明确新旧接口的兼容、迁移和弃用策略 |
| 数据迁移 | 明确旧数据转换、保留、失败恢复和验证方式 |

不要把缺陷包装成行为契约，也不要把历史实现细节误认为必须保持的外部约定。反过来，也不能未经评估就改变用户可观察行为、数据格式或调用契约。

## 七、评估变更影响

在选定方案之前，识别本次修改可能影响的范围。按实际情况检查：

| 影响维度 | 检查内容 |
|---|---|
| 直接调用方 | 谁直接调用被修改的代码或接口 |
| 间接调用方 | 是否存在多级依赖、回调或动态调用 |
| 数据消费者 | 谁读取、转换或发布修改后的数据 |
| 状态关联 | 哪些缓存、快照、配置和持久化数据依赖它 |
| 外部接口 | 是否影响 API、IPC、协议、文件格式或配置 |
| 副作用 | 是否改变 I/O、事件、通知、权限或资源操作 |
| 生命周期 | 是否影响初始化、启动、停止、销毁和恢复 |
| 并发关系 | 是否影响线程安全、可见性和执行顺序 |
| 平台环境 | 是否影响系统版本、厂商实现或设备差异 |
| 构建发布 | 是否影响构建变体、依赖、打包、安装或升级 |

还应考虑：

- **反向影响**：上游调用者是否必须配合修改？
- **延迟影响**：重启、恢复、升级、重新加载或稍后消费数据时是否会出问题？
- **部分影响**：多个步骤只完成一部分时，系统会留下什么状态？

影响分析应围绕实际变更路径展开，不要求为了形式罗列与本次修改无关的风险。

## 八、比较候选方案并选择修改方式

对涉及多个类、状态、接口或运行路径的修改，不要直接把第一个可工作的方案当成最终方案。按问题性质比较必要的候选方式：

- 保持结构，仅修复局部实现；
- 复用已有能力；
- 扩展现有模块；
- 在模块内部整理或提取逻辑；
- 新增独立结构；
- 调整职责、状态归属或依赖；
- 拆分职责；
- 进行必要的局部或跨模块重构。

比较时关注：

- 是否正确解决目标问题；
- 职责和状态归属是否合理；
- 原有行为契约是否得到正确处理；
- 调用链、数据流和依赖是否更清楚；
- 是否新增同步、生命周期、失败恢复或兼容成本；
- 是否将复杂度转移给其他模块或调用者；
- 测试、调试和维护是否更容易；
- 修改范围是否包含不必要的变化。

不需要向用户展示所有候选方案，但对于重大结构变化，应能解释为什么选择当前方案，以及为什么没有选择明显可行的替代方案。

# 第二部分：按实际变更类型触发的专项规则

## 九、专项规则的使用方式与判定等级

以下专项规则不是每次修改都要全部执行的通用清单，而是**根据实际准备改变的代码、状态、接口和运行机制触发**。任务名称不能代替变更分析；一次修改可以同时触发多个类型，相关规则应叠加执行。

为避免把所有检查项误解为同一种“准入条件”，统一使用以下三种判定等级：

| 等级 | 含义 | 不满足时的处理 |
|---|---|---|
| **硬性门槛（G）** | 对应方案必须满足的约束，不能用其他收益抵消 | 不得按当前方案实施；调整方案、补足前提或缩小范围 |
| **必须检查项（C）** | 必须调查并形成判断，但结果取决于实际情况 | 未查明时标记待证实；根据风险决定是否暂停、先做诊断或采用可逆措施 |
| **验收条件（A）** | 实施后必须按适当方式验证的结果 | 未验证不得宣称通过；说明缺口和剩余风险 |

执行规则：

1. 每类专项条件中的 G、C、A 分别具有上述含义，不得把检查项或验收项误写成实施前一律否决的硬门槛。
2. **职责拆分五项条件是明确例外：五项全部属于硬性门槛，必须 AND 全部通过。**
3. 证据不足不等于通过。对硬性门槛，证据不足按待证实处理，不得实施该方案；对其他检查项，必须明确不确定性及其风险。
4. 不涉及的专项规则无需填写或强行分析；简单修改可以简化证据形式，但不能忽略与该修改直接相关的关键约束。
5. 专项条件是最低要求，不是评分表。不能用“多数通过”抵消关键失败，也不应为了凑齐条目制造无意义分析。
6. 对硬性门槛以及会实质影响方案选择的检查结论，应记录可追溯的代码依据、调用路径、测试结果、运行日志或其他适当证据。不能仅复述规则、描述设计意图或把未经验证的假设当作通过依据。
7. 结论必须与证据等级相匹配：代码审查只能支持代码审查结论，静态检查只能支持相应静态检查结论，不能据此宣称运行行为已验证。简单低风险修改不要求制作冗长证据报告，但不得隐瞒关键依据和不确定性。

### 典型任务的规则触发示例

| 任务 | 通常触发的规则 | 不应机械触发的规则 |
|---|---|---|
| 只调整一处 UI 文案 | 通用需求确认、局部检查 | 不应自动执行完整架构、并发或状态审查 |
| 修复一个可复现的空指针 Bug | Bug 修复；若涉及共享状态，再叠加状态规则 | 不应仅因改动位于某个 Service 就自动触发职责拆分 |
| 新增一个带持久化的筛选功能 | 功能新增、状态与数据；若修改模块接口，再叠加接口规则 | 不应默认新建独立子系统 |
| 将现有 Service 的状态管理职责迁移到新组件 | 新增结构、职责拆分；按实际情况叠加状态和生命周期规则 | 不能只执行普通新增类检查而跳过五项拆分门槛 |
| 修改数据库字段或配置格式 | 状态与数据、兼容性；若影响调用协议，再叠加接口规则 | 不应只验证新版本能否启动 |
| 修复跨进程异步恢复失败 | Bug 修复、状态与数据、并发与生命周期；必要时叠加接口规则 | 不应只增加重试并只验证正常启动路径 |
| 为热点路径增加缓存 | 性能优化、状态与数据；共享缓存时叠加并发规则 | 不应只凭代码推测宣称性能提升 |
| 删除历史文件或清理旧配置 | 删除与清理；涉及用户数据时执行数据保护和恢复检查 | 不应仅凭静态无引用就删除持久化数据 |

这些示例用于说明触发逻辑，而不是固定模板。实际触发范围应由代码变化及其影响决定。

## 十、Bug 修复

**适用场景：** 修复错误结果、异常、崩溃、状态不一致、功能失效、资源泄漏或其他已观察到的问题。

| 等级 | 必须处理的事项 |
|---|---|
| C | 明确触发条件、实际表现、预期表现及相关环境；信息不足时列出未知项 |
| C | 找到与问题具有因果关系的原因，区分直接原因、根本原因和伴随现象；若尚未确认，列出假设及验证方式 |
| G | 不得将仅隐藏症状、吞掉异常或无依据增加重试的方案宣称为根因修复；临时缓解必须明确标注为缓解措施 |
| C | 明确本次要改变的错误行为，以及必须保留的相关正确行为和其他调用路径 |
| A | 通过复现测试、回归测试或其他针对性证据验证修复效果；无法复现时说明替代证据和剩余不确定性 |

典型错误：只在失败位置增加重试；吞掉异常让流程表面继续；增加特殊判断却不解释状态为何进入该分支；修复一个调用路径却遗漏同一根因影响的其他路径。

## 十一、功能新增与功能调整

**适用场景：** 新增业务能力、改变已有功能、调整交互或修改业务规则。

| 等级 | 必须处理的事项 |
|---|---|
| G | 明确需求目标和可观察行为；不得用未确认的假设替代需求 |
| C | 明确触发条件、输入、输出、成功结果、边界情况和不处理的情况 |
| C | 确定由哪个现有模块或新结构负责，不能仅选择最容易修改的位置 |
| C | 检查调用链、数据流、状态、权限、错误处理和必要生命周期 |
| G | 不得无说明地改变需求范围外的既有正确行为或绕过现有安全、权限约束 |
| A | 为主要成功路径、关键边界和必要异常路径定义并执行适当验证 |

典型错误：只实现演示路径；遗漏权限或异常处理；让新功能绕过现有业务入口；改变原功能行为却没有说明；为了一个小功能引入过大的通用框架。

## 十二、代码复用与现有模块扩展

**适用场景：** 计划复用既有代码，或在既有模块中增加能力。

| 等级 | 必须处理的事项 |
|---|---|
| C | 比较语义、职责、输入输出、异常、时序和行为契约，不能只凭代码相似判断 |
| G | 语义或契约实质不兼容时，不得强行合并为同一通用实现；应保留差异或重新设计抽象 |
| C | 确认被复用或扩展的模块本来就拥有该职责，或新能力确实是其自然延伸 |
| C | 检查是否引入不相关依赖、共享可变状态、隐式耦合或特殊分支 |
| C | 检查是否让其他调用者承担新的内部配置、状态或生命周期管理 |
| A | 评估复用或扩展后是否减少了重复和行为分歧，同时没有提高整体维护成本 |

判断原则：代码相似不代表业务语义、变化原因、错误处理和生命周期相同。复用不应把差异塞进充满条件分支的通用组件；扩展不应使原模块逐渐失去内聚性。

## 十三、新增结构与职责拆分

### 13.1 新增类、模块或抽象

**适用场景：** 新增类、模块、接口、服务、管理器、适配器或其他独立结构，但不一定涉及从旧模块转移已有职责。

| 等级 | 必须处理的事项 |
|---|---|
| G | 新结构必须服务于当前需求或当前已识别的问题，不得仅为假设中的未来需求建立完整体系 |
| C | 明确它负责什么、不负责什么、由谁使用，以及与现有结构的边界 |
| C | 明确其状态、资源、创建和销毁责任；无状态结构也应说明其依赖边界 |
| C | 检查新增接口、调用层级和协作关系是否真正必要 |
| A | 证明新结构带来的维护、测试、理解或运行成本与实际收益相称 |

新增结构不等同于职责拆分。无状态纯计算类、协议模型或独立适配器可能是合理新增；但不能仅因为命名为 Helper、Adapter 或 Manager 就默认合理。

### 13.2 职责拆分：五项强制准入条件

**适用场景：** 将原模块已经承担的一项职责迁移给具有独立边界的类、模块、服务、管理器或其他组件，从而改变职责承担者、状态管理边界或组件协作关系。

**任何职责拆分必须同时满足以下五项条件。五项全部是硬性门槛，构成 AND 关系，不是可互相补偿的评分项。任意一项不满足或证据不足，都不得按该拆分方案实施。**

1. **存在可以独立描述的职责。** 能说明新组件负责什么、不负责什么、与原模块的边界在哪里，以及为什么需要独立存在。代码行数、方法数量、文件过大、符合某种模式或未来可能扩展，都不能单独构成拆分理由。
2. **有明确的状态所有权。** 明确逻辑权威状态源、写入权限、提交责任、读取方式、派生数据和生命周期。判断所有权应看谁有权写入、提交和裁决冲突，而不是看字段或对象存放在哪个类中。读取副本、缓存和快照不自动构成状态所有者。若业务模型确需多个写入者，必须明确各自写入范围、一致性与冲突处理机制；拆分不得引入未定义的双重写入、重复状态或新的双向同步责任，也不得把所有权问题推给调用者。
3. **不破坏原来的副作用顺序。** 保持必要的可观察行为、因果顺序、异常传播、部分失败语义、重试和资源释放约束。不能只证明最终结果相同；涉及并发时还要保持必要的 happens-before 关系。
4. **不引入额外同步和生命周期复杂度。** 拆分不得增加整体同步复杂度或生命周期协调复杂度。检查锁、线程切换、消息协调、注册/注销、初始化顺序、关闭协议、跨组件握手和恢复路径；不能只比较锁数量，也不能把新增协调责任转移给调用者。若实现形式发生变化，必须证明整体同步与生命周期约束没有增加。
5. **不让调用者需要理解更多内部实现细节。** 调用者不应新增内部组件编排、状态传递、初始化销毁、重试、同步或实现专属配置的责任。原模块可以在内部协调新组件，但应尽量保持原有业务入口和抽象层级。

五项条件的证据要求：

| 条件 | 适当证据 | 不通过的典型表现 |
|---|---|---|
| 独立职责 | 职责定义、边界说明、现有代码映射 | 只是移动代码或缩短类 |
| 状态所有权 | 状态读写路径、权威源和生命周期说明 | 多个可写副本、双向同步、所有权模糊 |
| 副作用顺序 | 调用链、时序关系、行为或特征测试 | I/O、事件、状态写入或异常语义改变 |
| 同步与生命周期 | 线程、同步、初始化、关闭和恢复对比 | 新增协调协议、线程跳转或失效路径 |
| 调用者负担 | 修改前后调用点和接口对比 | 调用者需要编排内部组件 |

判定结果只能为：

- **通过**：五项均有证据证明满足，可以继续评估拆分必要性；
- **不通过**：至少一项明确不满足，不应采用该拆分方案；
- **待证实**：存在不确定项或证据不足，不得按已通过处理。

五项条件是拆分的必要准入条件，不是拆分的充分条件。即使全部通过，仍须证明原结构存在需要改善的问题，拆分带来明确收益，且该收益无法通过更简单的内部整理获得。

### 13.3 普通内部整理不应被误判为职责拆分

以下操作通常不构成职责拆分，不必机械执行完整五项准入检查：

- 提取私有方法以改善命名和阅读；
- 将确定性计算提取为无状态纯函数；
- 调整同一模块内部的私有类型或代码组织；
- 不改变职责所有权、调用边界和生命周期的文件整理。

但必须按实际影响判断，不能只看可见性或文件位置。如果所谓方法提取实际引入独立状态、生命周期、同步或新的组件协作关系，仍应视为职责拆分。

### 13.4 拆分条件未通过时的替代方式

不通过拆分不意味着只能保留糟糕结构。根据失败原因考虑：

- 提取私有方法或局部函数；
- 在原模块内重组代码和私有类型；
- 提取无状态纯函数；
- 在原模块内部建立更清晰的实现分区；
- 由现有组件继续承担职责，调整其内部实现；
- 先解决状态、时序或接口问题，再重新评估是否有必要拆分。

不得通过把新组件改名为 Helper、Util、Facade 或 Adapter 来规避拆分准入条件。

## 十四、接口与依赖变化

**适用场景：** 修改公共或模块间接口、方法语义、数据协议、依赖方向、依赖版本、注入方式或跨模块协作方式。

| 等级 | 必须处理的事项 |
|---|---|
| C | 说明为什么现有接口或依赖不能合理满足需求 |
| C | 识别直接、间接、静态、动态和配置驱动的使用者 |
| C | 明确参数、返回值、错误、时序、副作用和语义变化 |
| G | 破坏兼容性时，必须有明确需求或迁移决策，不得无说明地破坏既有调用方或数据协议 |
| C | 检查依赖方向，避免循环依赖、跨层反向依赖或不必要的传递依赖 |
| A | 验证受影响调用路径、协议兼容性和必要的构建变体 |

接口签名不变不代表契约不变。例如同步操作改成异步提交、异常从抛出改成吞掉、返回值从权威数据变成缓存值，都属于契约变化。

## 十五、状态、数据与配置变化

**适用场景：** 修改内存状态、配置、缓存、快照、数据库、文件、序列化格式、持久化数据或状态转换逻辑。

| 等级 | 必须处理的事项 |
|---|---|
| G | 对同一逻辑状态必须明确权威来源、写入权限和提交责任；不得引入未明确说明并论证一致性机制的多个权威写入者 |
| C | 明确谁可以创建、修改、删除、重置和提交数据，其他组件如何读取或请求更新；判断所有权看逻辑写入权与冲突裁决权，而不是字段或对象的物理存放位置 |
| C | 说明缓存、快照、派生值、副本和持久化数据如何保持一致、失效或重建 |
| C | 覆盖初始化、加载、更新、提交、失效、恢复和销毁 |
| C | 考虑部分写入、旧格式、重复执行、迁移失败和恢复方式 |
| A | 验证关键状态转换、数据完整性、兼容性和持久化结果 |

特别检查：

- 是否出现多个组件同时拥有同一逻辑状态的写入权；若确需多个写入者，是否明确各自写入范围、提交协议、一致性保证、冲突裁决和故障恢复；
- 是否把数据存放位置误当成状态所有权，或把只读副本、缓存和快照误判为权威状态源；
- 状态更新成功但事件发布失败时如何处理；
- 内存状态与持久化状态不一致时以谁为准；
- 缓存失效、进程重启和服务恢复时如何重建；
- 数据迁移是否幂等，部分失败后能否安全重试；
- 新旧版本或新旧格式交叉使用时是否兼容。

不能只通过检查字段赋值或编译结果判断状态修改正确。

## 十六、并发、异步、生命周期与资源变化

**适用场景：** 修改线程、进程、执行器、异步任务、回调、锁、服务启动停止、资源获取释放或恢复机制。

| 等级 | 必须处理的事项 |
|---|---|
| C | 确认操作运行在哪个线程、进程、执行器或回调上下文 |
| C | 确认调用、执行、完成、可观察顺序及必要的 happens-before 约束 |
| G | 不得破坏正确性所必需的互斥、可见性、原子性或顺序约束 |
| C | 覆盖创建、注册、启动、使用、停止、注销、关闭和重新初始化 |
| C | 考虑超时、取消、重复调用、线程或进程死亡、部分初始化和恢复 |
| A | 验证关键竞争、时序、关闭和资源释放路径，检查线程、句柄、文件、监听器和任务不会泄漏或重复释放 |

不要因为使用线程安全容器、锁或异步框架就默认线程安全。必须结合具体访问路径、锁范围和生命周期判断。也不要为了代码分层而无必要地引入线程切换、异步队列、回调链或服务协调协议。

# 第三部分：按修改目标叠加的专项检查

## 十七、纯重构与代码整理

**适用场景：** 主要目的是改善代码组织、命名、可读性、内聚性或可维护性，不打算改变外部功能。

- **G：** 如果声明为纯重构，不得夹带未声明的功能、接口语义或数据行为变化；发现必须改变行为时，应明确重新界定任务。
- **C：** 说明当前结构或实现存在的具体问题，明确本次不打算改变的外部行为、接口和数据语义。
- **C：** 涉及副作用、并发和生命周期时，识别需要保持的行为约束。
- **A：** 使用适当测试、差异检查或行为对比证明结果符合预期。

纯重构原则上要求可观察行为等价。如果同时需要修复缺陷或改变功能，应明确区分变更目的和验证标准，避免将行为变化隐藏在重构中。

## 十八、代码删除与清理

**适用场景：** 删除代码、模块、配置、资源、文件、兼容逻辑或历史实现。

| 等级 | 必须处理的事项 |
|---|---|
| C | 确认待删除内容已经无用，或明确其替代方式 |
| C | 检查静态引用、反射、动态注册、配置驱动、序列化名称、脚本和外部调用 |
| G | 删除持久化数据、用户文件或兼容路径前，必须明确匹配范围、保留策略和误删风险 |
| C | 确认删除不会破坏旧数据读取、恢复、升级或降级路径 |
| A | 通过构建、测试和必要的运行检查验证删除结果 |

不能仅以 IDE 显示“没有引用”作为删除依据。动态调用、插件、反射和外部协议可能不出现在静态调用图中。清理用户数据时，还应明确失败恢复方式；不能为了清理方便而删除尚未确认安全删除的数据。

## 十九、性能优化

**适用场景：** 优化 CPU、内存、I/O、启动时间、响应延迟、吞吐量、电量或资源占用。

| 等级 | 必须处理的事项 |
|---|---|
| C | 明确优化对象、使用场景、性能指标和目标范围 |
| C | 尽可能建立修改前基线，识别真正的热点或瓶颈 |
| G | 不得为性能收益擅自破坏既定功能语义、数据一致性、安全性或必要精度 |
| C | 评估额外内存、复杂度、同步、缓存一致性和维护成本 |
| A | 使用可比较的测量或针对性验证确认收益，并检查功能与性能回归 |

不要仅凭代码看起来更快就宣称性能提升。没有测量数据时，应表述为“预期减少某项开销”，而不是“已提升性能”。避免没有依据地增加缓存、预加载、并发或复杂算法。

## 二十、兼容性、平台与依赖升级

**适用场景：** 修改系统 API、厂商适配、运行环境、语言或框架版本、第三方依赖、构建插件、协议和部署方式。

| 等级 | 必须处理的事项 |
|---|---|
| C | 明确目标平台、版本范围和支持边界 |
| C | 核对实际 API、依赖版本、权限和运行时限制 |
| C | 检查新旧环境、构建变体和条件分支 |
| G | 对旧数据、旧接口和新旧组件交互造成的不兼容，必须有明确的迁移或停止支持决策 |
| A | 在可用环境中验证代表性版本，并标记未覆盖环境 |

不要仅根据 API 名称或文档印象判断兼容性。对于平台差异、厂商行为和依赖变化，应尽量查阅项目实际使用版本的文档、源码或运行证据。

## 二十一、安全与权限相关修改

**适用场景：** 修改身份认证、授权、文件访问、网络访问、输入处理、敏感数据、密钥、权限或信任边界。

| 等级 | 必须处理的事项 |
|---|---|
| C | 明确受保护资源、主体身份和信任边界 |
| G | 不得为了让功能工作而绕过授权、放宽安全边界，或将无法确认的授权状态默认视为允许 |
| C | 明确授权规则、拒绝访问时的行为，并验证不可信输入 |
| C | 检查日志、异常、配置和持久化中是否泄漏敏感信息 |
| A | 验证允许与拒绝两类路径，并检查权限变化后的兼容性 |

安全相关修改不能只验证正常授权路径。应根据具体风险检查最小权限、输入校验、信任边界和敏感信息处理。

## 二十二、日志、错误处理与可观测性修改

**适用场景：** 修改日志采集、日志存储、错误传播、指标、诊断信息或故障报告。

| 等级 | 必须处理的事项 |
|---|---|
| C | 明确记录或报告的目的、触发条件和责任组件 |
| C | 检查日志量、文件增长、轮转、保留、磁盘占用和清理策略 |
| C | 保持错误级别、异常传播和关键诊断信息的语义清楚 |
| G | 不得将未脱敏的密码、密钥、访问令牌、认证材料，或超出授权与诊断必要范围的敏感个人及业务数据写入日志、异常信息、指标标签或诊断导出；不得让日志机制破坏关键业务正确性 |
| A | 验证正常、异常、长时间运行和资源不足等与本次修改相关的场景 |

日志不是无成本的副作用。持续采集、文件写入、压缩、轮转和清理都应考虑生命周期、失败处理及磁盘容量边界。确需记录敏感上下文时，应遵循数据最小化、必要脱敏、访问控制和合理保留期限，并避免将敏感值放入异常消息、指标标签或可导出的诊断内容。

# 第四部分：实施、验证与结果说明

## 二十三、确定修改范围与实施策略

实施前将变更划分为：

- **必要修改**：正确实现目标所必须改变的内容；
- **连带修改**：由于接口、依赖或数据变化而必须同步调整的内容；
- **无关修改**：与本次目标没有直接关系的优化、清理和重构。

应尽量减少无关修改，但不能为了追求最小 diff 而遗漏必要的调用方、测试、数据迁移或兼容调整。目标是**最小完整变更**，不是最少文件或最少行数。

对中等及以上风险的修改，应在实施前尽可能确认相关构建、测试和关键行为的现状基线；性能、资源占用、数据完整性或恢复行为属于本次目标或风险范围时，也应记录相应指标或状态基线。记录已有失败、警告、环境限制和未执行项目，避免把历史问题误归因于本次修改，也避免把新出现的问题未经调查就归为历史遗留。实施后应尽可能在相同环境、命令、数据和条件下对照验证。若无法建立基线，应明确说明缺失项及其对结论的影响。

对高风险变更，可以先建立基线和测试，再分阶段调整实现、接口和调用路径，以便定位回归来源。是否拆成多个阶段或提交，应由风险和可验证性决定，不应机械要求。

实施时：

1. 只修改已确定的必要范围；
2. 避免混入无关重构、依赖升级或大面积格式化；
3. 保持接口、状态和副作用边界清晰；
4. 对不可逆或部分成功的操作考虑保护措施；
5. 对并发和生命周期变化明确启动、停止、取消和清理责任；
6. 让新增异常、日志和测试与实际行为一致；
7. 不通过吞异常、跳过测试、放宽断言或屏蔽错误来制造表面成功。

## 二十四、处理失败、重试与恢复

根据修改影响评估是否需要事务、回滚、补偿或恢复机制，不要求每项修改都设计完整回滚系统。

对文件、数据库、用户配置、持久化状态、跨进程协议和服务生命周期修改，应按需检查：

- 操作执行到一半失败时会留下什么状态；
- 重试是否安全，是否可能重复执行副作用；
- 操作是否幂等，部分成功如何识别；
- 是否存在新旧版本或新旧格式交叉运行；
- 是否需要回滚、补偿、重新初始化或人工恢复；
- 无法回滚时，是否有明确的风险边界和数据保护措施。

不能为了形式给所有操作增加回滚层。恢复机制本身也会带来复杂度，必须与实际风险相称。

## 二十五、验证目标行为与回归行为

验证必须与本次修改目标对应。不能只以编译成功或测试数量作为完成标准。

| 修改目标 | 适当的验证方式 |
|---|---|
| Bug 修复 | 原问题复现测试、回归测试或针对性运行证据 |
| 功能新增 | 主要成功路径、输入边界、权限和异常路径 |
| 状态管理 | 状态转换、一致性、并发访问和恢复测试 |
| 副作用顺序 | 调用顺序、完成顺序、可观察行为和异常路径验证 |
| 接口变化 | 所有相关调用方、协议兼容和构建变体 |
| 数据变化 | 旧数据读取、迁移、部分失败、重试和完整性检查 |
| 并发与生命周期 | 竞争、取消、超时、死亡重连、关闭和资源释放测试 |
| 性能优化 | 修改前后可比较的指标、代表性负载和回归检查 |
| 兼容性修改 | 对应平台、版本、依赖和设备范围的验证 |
| 代码删除 | 构建、静态引用、动态引用和运行路径检查 |

按实际风险选择测试组合，不要机械要求所有测试类型。尽可能在实施前确定验证标准，并优先建立能够复现原问题或保护关键行为的测试。对中等及以上风险修改，应结合第二十三节记录的实施前基线对照结果；不能建立基线或无法进行同条件对照时，应明确说明原因和验证局限。

## 二十六、区分验证证据等级

结果说明必须区分：

- **已运行并通过**：确实执行了对应测试或命令，结果成功；
- **已静态检查**：通过代码检查、类型检查、静态分析或构建检查；
- **已代码审查**：根据源码和调用关系完成分析，但未运行相关场景；
- **推断符合预期**：基于实现作出推断，尚无直接验证；
- **未验证**：当前环境或条件不允许验证；
- **验证失败**：已执行但未通过，应说明具体失败。

不能将“未发现问题”写成“已证明没有问题”，不能将“编译通过”写成“功能正确”，也不能将“测试未覆盖”写成“测试通过”。

如果测试环境、设备、依赖或权限不足，应明确说明未验证范围及其风险，不要虚构执行结果。

## 二十七、修改后的整体复核与决策记录

完成修改后，检查：

- 是否满足用户目标和验收条件；
- 本次允许改变的行为是否按预期变化；
- 不属于本次范围的既有正确行为是否保持；
- 是否遗漏调用者、数据消费者、配置或构建变体；
- 是否出现新的状态所有权、依赖或生命周期问题；
- 是否增加不必要的抽象、特殊分支或同步关系；
- 是否留下部分失败、重试、恢复或数据迁移风险；
- 相关测试、日志和文档是否与实现一致；
- 整体复杂度是否与需求规模匹配。

对于职责拆分、接口变化、状态变化和并发变化，应复核对应专项规则；不能只检查最终编译结果。

当修改涉及多个模块、核心状态、接口、并发、持久化或明显架构变化时，应能够说明：

- 要解决的问题、目标行为和验收标准；
- 调查到的根因及证据，或尚未证实的假设；
- 本次需要改变和必须保持的行为；
- 主要影响范围；
- 选择当前方案的原因和重要替代方案；
- 修改引入或消除的复杂度；
- 执行过哪些验证；
- 哪些内容尚未验证及剩余风险。

对于具有长期影响的重大架构决策，可以记录 ADR 或简要设计说明。普通局部修改不需要为了形式创建决策文档。是否向用户展示完整分析，应服从用户要求；但关键依据、未验证项和风险不能被隐瞒。

# 第五部分：错误模式、统一流程与最终自检

## 二十八、常见错误决策模式

### 1. 没有理解需求就直接实现

```text
看到一句需求 → 选择熟悉的方案 → 开始编码
```

应先确认目标行为、保留行为、约束和验收标准。

### 2. 把现象当成根因

```text
某处失败 → 在该处增加重试或特殊判断
```

应沿调用链、状态和副作用查明失败原因。

### 3. 为了最小修改而遗漏必要影响

```text
只修改报错文件 → 不调整调用者、数据或测试
```

应完成必要的最小完整变更，只减少无关修改。

### 4. 为了复用而合并语义不同的代码

```text
两处代码相似 → 强行抽成通用组件
```

应比较职责、行为契约、变化原因和生命周期。

### 5. 为了避免新增而持续堆叠逻辑

```text
不允许新增 → 不断给现有类增加分支和状态
```

应根据真实职责和整体复杂度评估结构调整。

### 6. 为了架构清晰而过度拆分

```text
每项操作一个类 → 多级转发和协调
```

应通过职责拆分五项硬性门槛，并证明拆分确有必要。

### 7. 用表面结果掩盖行为变化

```text
最终值相同 → 认为修改等价
```

应检查时序、异常、部分失败、资源释放和调用者可观察行为。

### 8. 忽略兼容性和历史数据

```text
新版本能够运行 → 认为升级安全
```

应检查旧配置、旧数据、旧接口和升级恢复路径。

### 9. 把编译通过当成修改完成

```text
构建成功 → 宣称问题解决
```

应根据目标行为执行适当验证，并如实报告证据等级。

### 10. 把无关优化混入当前任务

```text
顺手重构 → 顺手升级依赖 → 顺手重做其他模块
```

应控制无关变化；发现额外问题时记录并单独评估，不要未经必要性分析就扩大范围。

## 二十九、统一项目修改流程

```text
收到项目修改需求
    ↓
确认修改目标、约束和验收标准
    ↓
区分本次需要改变与必须保持的行为
    ↓
调查相关代码、调用链、状态、数据流和生命周期
    ↓
诊断问题根因（适用于问题修复或优化）
    ↓
分析直接、间接、延迟和跨环境影响
    ↓
识别实际涉及的修改类型
    ↓
触发并叠加对应专项规则
    ↓
比较局部修复、复用、扩展、内部整理、新增、拆分或重构
    ↓
选择整体风险和复杂度合理的方案
    ↓
确定修改范围、失败处理和验证方式
    ↓
实施修改
    ↓
验证目标行为、回归行为和相关质量属性
    ↓
复核整体架构、兼容性和失败路径
    ↓
说明结果、证据等级和剩余风险
```

简单任务可以缩短流程，但不能跳过与该任务直接相关的需求确认、关键影响检查和结果验证。涉及多个领域时，应叠加专项规则，而不是只按任务标题选择一个类别。

## 三十、最终自检

### 需求与行为

- 是否准确理解用户要改变什么？
- 是否明确本次必须保持和允许改变的行为？
- 验收条件是否与修改目标对应？

### 调查与诊断

- 是否理解了足以覆盖修改范围的现有系统？
- 是否找到问题根因，或明确标记尚未证实的假设？
- 是否检查相关调用链、数据流、状态和生命周期？

### 方案与架构

- 当前修改方式是否适合真实职责？
- 是否比较过必要的替代方案？
- 是否避免强行复用、无意义新增和过度拆分？
- 若涉及职责拆分，五项硬性门槛是否全部有证据通过？
- 是否把复杂度转移到了调用者、状态同步或生命周期中？

### 影响与风险

- 是否识别直接和间接调用方、数据消费者及外部接口？
- 是否考虑异常、重试、部分失败、恢复和兼容性？
- 是否检查与本次修改相关的安全、性能、并发和资源风险？

### 实施与验证

- 修改范围是否包含所有必要内容，同时避免无关变化？
- 是否验证本次目标行为？
- 是否回归检查不应改变的既有行为？
- 是否如实区分已运行、静态检查、代码审查、推断和未验证？

### 最终判断

> **本次修改是否正确解决了目标问题，同时保护了不应改变的行为，并且没有引入不必要的结构、依赖、状态、同步、生命周期或维护成本？**

如果不能清楚说明修改目标、根因或设计依据，应继续调查或明确不确定性；如果验证不足，应如实说明限制，而不是用“看起来合理”代替证据。

## 三十一、最终原则

> **先理解用户要改变什么，再理解项目当前如何工作。**
>
> **先调查问题根因和影响范围，再决定修改位置和实现方式。**
>
> **保护既有正确行为，不保护已确认的缺陷。**
>
> **复用、扩展、新增、拆分和重构都是工具，不是目的。**
>
> **职责决定结构，状态必须有清晰的权威所有者。**
>
> **控制无关修改，不以最少文件或最小 diff 为最高目标。**
>
> **职责拆分必须通过五项强制准入条件；其他修改按实际类型执行相应的硬性约束、检查项和验收条件。**
>
> **复杂度应在整个受影响系统中衡量，不能转嫁给调用者、状态同步或生命周期。**
>
> **修改完成必须验证目标行为和回归行为，并如实说明证据与未验证风险。**
>
> **架构规则服务于正确、可靠的项目修改，而不是让项目修改迁就架构规则。**
