# 红石语法与供电追踪

配合 `version-facts-1.12.md` 使用。这里只讲**怎么用**（追踪算法），不重复钉板里的数值表。

---

## 1. 命令方块的四种触发来源

分析任何 `auto=0` 的命令方块时，按这个顺序穷举，不要只做 6 面扫描：

| 顺序 | 机制 | 判据 | 追踪动作 |
|---|---|---|---|
| 1 | **玩家进入区域** | 命令以 `execute @a[...x=..,dx=..]` 开头 | 记录选择器 box；此方块不需红石 |
| 2 | **被 chain 触发** | 存在 `chain` 边指向它 | 沿 chain 边回溯找链头 |
| 3 | **比较器供电** | 存在 `comparator` 边指向它 | 沿比较器朝向往回找被读取的命令方块 |
| 4 | **红石直接/间接供电** | 6 面有电源元件 | 见 §2 |
| 5 | **setblock 交接** | 命令是 `setblock <pos> minecraft:redstone_block` | 去 `<pos>` 的 26 邻域找受电方块 |

> 顺序有讲究：1~3 是"非红石"触发，先排除掉，剩下的才是红石问题。
> 反过来做会把大量 chain 触发误报成"缺电源"。

## 2. 红石供电追踪算法

### 2.1 直接邻接（L1）

6 面（±X, ±Y, ±Z）内存在下列之一即得电：
`redstone_block(152)` / `redstone_torch(76)` / `lever(69)` / `wooden_button(143)` /
`stone_button(77)` / `light_weighted_pressure_plate(147)` / `heavy_weighted_pressure_plate(148)` /
`daylight_detector(151)` / `powered_comparator(150)` / `powered_repeater(94)` /
`activator_rail(157)`。

**火把的陷阱**：火把**附着**在方块上时是**反相器**——附着面不供电，其余面供电。
判断附着面：火把的 meta 指向被附着的方向（`version-facts-1.12.md` §3）。
若目标方块正是火把附着的那个块，则该方块**得不到**这个火把的信号。

**红石块的陷阱**：红石块给 6 面供电，但对**它自己所在的方块**无效。

### 2.2 中继器（L2）

中继器**只给正前方**供电。1.12 中继器 meta：bits2-3 = 朝向（0=south 1=west 2=north 3=east），
bits0-1 = 延迟-1。

判定：若中继器位于 `C`，则其输出目标是 `C + facing_delta`。
只有 `C + facing_delta` 恰好是目标方块时才算供电。延迟 = `(meta & 3) + 1` tick。

### 2.3 红石粉网络（L3）

红石粉**正交**连通（不斜向），连接相邻的粉 / 电源 / 受电方块。
1.12 中红石粉的 data 存的是**信号强度 0-15**（不是连接形状），形状由邻居推导。

追踪：从目标方块相邻的粉出发做 BFS，收集整个粉连通域；
若域内任一格的 6 面邻接电源元件，则该域被供电。
注意粉网络可以绕行十几格，且**可以跨越不同 y 层**。

### 2.4 粉网络的边界

粉网络追踪会遇到三种"追不下去"的情况，都应标为 `needs_manual_trace` 而不是猜：

| 情况 | 含义 |
|---|---|
| 网络延伸到 box 外 | 作用域不足 → **升级作用域**后重跑 |
| 网络末端没有任何电源 | 可能被中继器锁存/反向，或电源在 box 外 |
| 网络自相连接（环形） | 需要判断锁存状态（ring lock），超出静态分析能力 |

## 3. 跨 tick 交接：`setblock` 建电源

命令方块执行 `setblock <pos> minecraft:redstone_block` 时：

```
tick T   : TE 相位 —— 红石块落地，通知邻居
tick T+1 : TT 相位 —— 目标命令方块获得供电并执行
```

→ **交接边延迟 = 1 tick**。

判定 `<pos>` 的受电方块时，**必须查 26 邻域**而非 6 邻域：
红石块对 6 面供电，但红石粉可以从斜向接入、比较器可以从侧面来。

**plumbing vs gameplay 判定**（迁移前的必做项）：

| 角色 | 判据 | 迁移处理 |
|---|---|---|
| `plumbing` | 目的是让某个命令方块获得供电/触发 | 迁移到函数后**删除**，改由状态机控制顺序 |
| `gameplay` | 目的是改变世界（关门、封路、造景） | **保留** |

误判后果：删掉 gameplay 会让副本门永远开着；保留 plumbing 会让每 tick 重复触发。

**R4 的价值**：每个 `setblock <pos> redstone_block` 必须在**同坐标**有对应的 `setblock <pos> air`
（或别的移除动作），否则那个电源**永久存在**，下游所有时序都变。没有配对的 `setblock air`
往往正是设计者故意留的常驻电源（例如做成一条"红石总线"）——但那需要显式确认，不能默认。

## 4. 比较器读命令方块的成功计数

1.12 比较器（`unpowered_comparator` id 149 / `powered_comparator` id 150）：
bits0-1 = 朝向（0=south 1=west 2=north 3=east），bit2 = 减法模式。

**输入在背后，输出在正前方**。所以位于 `C`、朝向 `F` 的比较器：

```
读取 C - F   （被比较方块，例如命令方块的成功计数）
供电 C + F   （输出的目标）
```

这是 1.12 里**把布尔结果变成红石信号**的标准做法，也是把"命令成功与否"接入红石电路的唯一途径。
分析时若看到 `auto=0` 的命令方块周围有比较器，优先走这条。

## 5. 1.12 没有的东西（别去找）

| 想做的事 | 1.12 的实际做法 |
|---|---|
| "实体死亡时减计数" | 无原生回调 → `testfor` 判空 / 死亡代理盔甲架 / 玩家击杀增量 |
| "检测选择器是否匹配" | `execute if @e` 是 1.13+ → 用 `testfor`（且 `testfor` 只给 0/1，不给数量） |
| "把命令结果存进计分板" | `execute store` 是 1.17+ → 用 `stats entity ... set SuccessCount` |
| "函数提前返回" | 无 `return` → 嵌套守卫函数 |
| "读取命令执行数量" | `stats entity ... set AffectedEntities`（1.12 有限支持，且有时序陷阱） |

## 6. 建议的追踪顺序（实操 checklist）

```
1. 列出所有 auto=0 的命令方块                        → 排除 auto=1 的自跑链
2. 对每个 auto=0：
   a. 命令是 execute @a[box] ?            → 玩家触发，记录 box
   b. 有 chain 边指向它 ?                 → chain 触发，回溯链头
   c. 有 comparator 边指向它 ?            → 比较器供电，回溯被读取方块
   d. 6 面有电源 ?                        → 直接供电，记录延迟
   e. 相邻有红石粉 ?                      → BFS 粉网络，看是否接到电源
   f. 都不成立                             → needs_manual_trace，考虑升级作用域
3. 对所有 setblock 红石类命令：
   a. 记下目标坐标，扫描 26 邻域的受电方块   → 交接边
   b. 查同坐标是否有移除命令                → R4
   c. 判定 plumbing / gameplay              → 迁移决策
4. 走 chain 图，检查是否有环                → R5（三色 DFS）
5. 跑全部审计规则
```
