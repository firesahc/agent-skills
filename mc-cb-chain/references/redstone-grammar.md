# 红石语法与供电追踪

配合 `version-facts-1.12.md` 使用。这里只讲**怎么用**（追踪算法），不重复钉板里的数值表。

---

## 0. 控制室的标准接线：1.12 的四原语

1.12 副本的红石电路**没有想象中复杂**。绝大多数副本的"逻辑层"只用下面四种元件，
按固定套路拼成一条 **lane**（固定 y,z、沿一个方向排列的一行命令方块）。
**先认这四种元件，再看具体电路。**

```
[① repeating 传感器] ─成功计数─▶ [② 比较器] ─▶ [实心方块] ─▶ [③ 红石火把] ─▶ [④ impulse 动作头] ─▶ [chain…]
```

| # | 元件 | 角色 | 关键语义 |
|---|---|---|---|
| ① | **repeating 命令方块**（id 210） | **传感器**：每 tick 求值一次 | 典型命令 `testfor @e[…]` / `scoreboard players test …`；<br>**`auto` 在此无意义**——每 tick 自跑，不需要任何电源；<br>它的**成功计数**（0/1）是下游唯一的输入信号 |
| ② | **比较器**（id 149 / 150） | **桥梁**：把"命令结果"变成红石信号 | **后方（输入）读命令方块的成功计数**，**正前方（输出）送电**；<br>可以隔一个**导体块**（实心方块）读取，比较器会忽略中间块的通电强度；<br>固有延迟 **2 tick** |
| ③ | **红石火把**（id 76） | **反相器**（可选） | 比较器输出点亮一块实心方块 → **附着其上的火把熄灭** → 火把点亮动作头。<br>⇒ **传感器"失败"时才触发**；<br>不装反相器 ⇒ **传感器"成功"才触发** |
| ④ | **impulse 命令方块**（id 137） | **动作头**：真正执行的一环 | `auto=0`，由红石**上升沿**触发 ⇒「条件由假变真」只触发一次；<br>信号持续为真**不会**重复执行 |

### 0.1 两种典型 lane

**A 型 · 状态推进（"上一类敌人全灭才推进"）—— 带反相器**

```
[① repeating: testfor 实体X]  → 失败（实体已死）
   → ② 比较器输出 0 → 实心方块不通电 → ③ 火把亮 → ④ 动作头得电 → 执行
```

**B 型 · 概率技能（"抽签命中才放大招"）—— 不带反相器**

```
[① repeating: scoreboard players test 抽奖 几率 0 2]  → 成功
   → ② 比较器输出 1 → 直接点亮 ④ 动作头 → 执行
```

> **B 型常把一条 lane 切成两段**：第一段末尾放一个
> `scoreboard players test 抽奖 几率 0 2`，其后紧跟一个**比较器**——
> **比较器不是命令方块，会把 chain 断开**。比较器再点亮第二个 **impulse** 动作头，
> 开启第二段 chain。这样"抽签"只负责**当闸门**，技能本体仍留在 chain 里，
> 且两段之间天然隔开 2 tick。

### 0.2 读这张图时的四个必查项

1. **比较器是不是真在读命令方块？** → 被读取方块必须在比较器**正后方**；
   中间隔一个实心方块也行（导体块）。若两侧都不是命令方块，这只比较器不产生有效闸门。
2. **火把的附着侧对不对？** → 火把**不给自己附着的方块**供电，其余 5 面供电。
   判定用 `version-facts-1.12.md` §3 的**附着侧**表（`0`上 `1`西 `2`东 `3`北 `4`南 `5`下）。
   把它读反，就会把"被火把点亮的动作头"误判成"火把附着的方块"。
3. **动作头是上升沿还是常亮？** → 若电源是 `setblock <pos> redstone_block` 建立的**常驻**电源，
   impulse **只在电源建立那一刻执行一次**；之后必须有人把电源拆掉才能再次触发。
   这既是设计者常用的"一次性闩锁"，也是"副本只触发一次"类故障的最常见来源。
4. **有没有"二级传导"？** → **被直接供电的实心方块会把电力传给相邻命令方块**
   （钉板 §3.2）。典型形态：`压力板 → 混凝土 → 命令方块`、
   `火把 → 红石粉 → 标记块 → 命令方块`。**追踪时不能只看 6 面直邻**，要顺着
   "被供电的实心方块"再走一跳。

## 1. 命令方块的四种触发来源

分析任何 **impulse**（`auto=0`）的命令方块时，按这个顺序穷举，不要只做 6 面扫描：

| 顺序 | 机制 | 判据 | 追踪动作 |
|---|---|---|---|
| 1 | **玩家进入区域** | 命令以 `execute @a[...x=..,dx=..]` 开头 | 记录选择器 box；此方块不需红石 |
| 2 | **被 chain 触发** | 存在 `chain` 边指向它 | 沿 chain 边回溯找链头 |
| 3 | **比较器供电** | 存在 `comparator` 边指向它 | 沿比较器朝向往回找被读取的命令方块 |
| 4 | **红石直接/间接供电** | 6 面有电源元件 | 见 §2 |
| 5 | **setblock 交接** | 命令是 `setblock <pos> minecraft:redstone_block` | 去 `<pos>` 的 26 邻域找受电方块 |

> 顺序有讲究：1~3 是"非红石"触发，先排除掉，剩下的才是红石问题。
> 反过来做会把大量 chain 触发误报成"缺电源"。
>
> **作用域提醒**：R2（"必须能指出触发来源"）只对 **impulse** 成立。
> `auto` 字段在 repeating / chain 上没有语义——repeating 每 tick 自跑，chain 被链触发，
> 二者都不需要电源。用 `auto==0` 去筛 repeating 传感器，会把它们全部误报成"缺电源"。

## 2. 红石供电追踪算法

### 2.1 直接邻接（L1）

6 面（±X, ±Y, ±Z）内存在下列之一即得电：
`redstone_block(152)` / `redstone_torch(76)` / `lever(69)` / `wooden_button(143)` /
`stone_button(77)` / `light_weighted_pressure_plate(147)` / `heavy_weighted_pressure_plate(148)` /
`daylight_detector(151)` / `powered_comparator(150)` / `powered_repeater(94)` /
`activator_rail(157)`。

**火把的陷阱**：火把**附着**在方块上时是**反相器**——**附着面不供电**，其余 5 面供电。
判断附着面：查 `version-facts-1.12.md` §3 的**附着侧**表
（`0`=上 `1`=西 `2`=东 `3`=北 `4`=南 `5`=下；即 meta 直接编码"挂靠的实心方块在哪一侧"）。
若目标方块正是火把附着的那个块，则该方块**得不到**这个火把的信号。

**红石块的陷阱**：红石块给 6 面供电，但对**它自己所在的方块**无效。

**二级传导的陷阱（务必多走一跳）**：**被直接供电的实心方块会把电力传给相邻命令方块**。
所以"命令方块 6 面内没有电源"**不等于**"它没被供电"——中间隔着一个被点亮的实心方块，
照样能点亮它。典型两跳形态：

```
压力板/火把/红石粉  →  实心方块(被直接供电)  →  命令方块
```

**追踪动作**：对每个 auto=0 的 impulse，先扫 6 面；若 6 面无电源，
再扫"6 面内被直接供电的实心方块"，命中即算得电（并注明是二级传导、延迟按源头算）。

### 2.2 中继器（L2）

中继器**只给正前方**供电。1.12 中继器 meta：bits2-3 = 朝向
（**0=north 1=east 2=south 3=west**，见钉板 §3.1），
bits0-1 = 延迟-1。

判定：若中继器位于 `C`，则其输出目标是 `C + facing_delta`。
只有 `C + facing_delta` 恰好是目标方块时才算供电。延迟 = `(meta & 3) + 1` tick。

### 2.3 红石粉网络（L3）

红石粉**正交**连通（不斜向），连接相邻的粉 / 电源 / 受电方块。
1.12 中红石粉的 data 存的是**信号强度 0-15**（不是连接形状），形状由邻居推导。

追踪：从目标方块相邻的粉出发做 BFS，收集整个粉连通域；
若域内任一格的 6 面邻接电源元件，则该域被供电。
注意粉网络可以绕行十几格，且**可以跨越不同 y 层**。

### 2.4 粉网络的边界

粉网络追踪会遇到三种"追不下去"的情况，都应标为 `needs_manual_trace` 而不是猜：

| 情况 | 含义 |
|---|---|
| 网络延伸到 box 外 | 作用域不足 → **升级作用域**后重跑 |
| 网络末端没有任何电源 | 可能被中继器锁存/反向，或电源在 box 外 |
| 网络自相连接（环形） | 需要判断锁存状态（ring lock），超出静态分析能力 |

## 3. 跨 tick 交接：`setblock` 建电源

命令方块执行 `setblock <pos> minecraft:redstone_block` 时：

```
tick T   : TE 相位 —— 红石块落地，通知邻居
tick T+1 : TT 相位 —— 目标命令方块获得供电并执行
```

→ **交接边延迟 = 1 tick**。

判定 `<pos>` 的受电方块时，**必须查 26 邻域**而非 6 邻域：
红石块对 6 面供电，但红石粉可以从斜向接入、比较器可以从侧面来。

**plumbing vs gameplay 判定**（迁移前的必做项）：

| 角色 | 判据 | 迁移处理 |
|---|---|---|
| `plumbing` | 目的是让某个命令方块获得供电/触发 | 迁移到函数后**删除**，改由状态机控制顺序 |
| `gameplay` | 目的是改变世界（关门、封路、造景） | **保留** |

误判后果：删掉 gameplay 会让副本门永远开着；保留 plumbing 会让每 tick 重复触发。

**R4 的价值**：每个 `setblock <pos> redstone_block` 必须在**同坐标**有对应的 `setblock <pos> air`
（或别的移除动作），否则那个电源**永久存在**，下游所有时序都变。没有配对的 `setblock air`
往往正是设计者故意留的常驻电源（例如做成一条"红石总线"）——但那需要显式确认，不能默认。

## 4. 比较器读命令方块的成功计数

1.12 比较器（`unpowered_comparator` id 149 / `powered_comparator` id 150）：
bits0-1 = 朝向（**0=north 1=east 2=south 3=west**，见钉板 §3.1），bit2 = 减法模式。

**输入在后方（rear），输出在正前方（front）**。所以位于 `C`、朝向 `F` 的比较器：

```
读取 C - F   （被比较方块，例如命令方块的成功计数）
供电 C + F   （输出的目标）
```

这是 1.12 里**把布尔结果变成红石信号**的标准做法，也是把"命令成功与否"接入红石电路的唯一途径。
分析时若看到 auto=0 的 impulse 周围有比较器，优先走这条。

### 4.1 四条必须记住的细节

| 细节 | 内容 | 后果 |
|---|---|---|
| **摆放位置** | 比较器要放在被读命令方块的**输出侧**、且与之**同向**（比较器的后方 = 该命令方块） | 放错方向 → 读不到成功计数，输出恒 0 |
| **可隔导体块** | 中间隔一个**实心方块**仍能读到，比较器**忽略中间块的通电强度** | 只看"紧邻"会漏判触发源 |
| **2 tick 延迟** | 信号穿过比较器要 2 game tick | 时序图上闸门与动作之间要留 2 tick，**不能填 0** |
| **比较器会断链** | 比较器不是命令方块，chain 到它就断了 | 一条 lane 常被比较器切成两段，第二段由比较器点亮的 impulse 开启 |

### 4.2 比较器读的是"成功计数"，不是"是否通电"

命令方块保存的是**最后一条命令的成功计数**（0/1），
在它**下一次执行之前不会改变**。
⇒ 比较器输出的是一个**滞后的状态位**，不是实时事件。
配合 §0.2 第 3 条：impulse 只吃**上升沿**，所以
"比较器输出 0→1" 才会触发一次，"1 保持不变"不会重复触发。

### 4.3 输出端落在实心方块上时

比较器的输出会点亮**正前方**的那块实心方块；该方块随即成为 *powered block*，
可以再**二级传导**点亮它旁边的命令方块（钉板 §3.2）。
这既是"反相器"接法的物理基础（§0.1 的 ③），也是很多"隔着墙的触发"的成因。

## 5. 1.12 没有的东西（别去找）

| 想做的事 | 1.12 的实际做法 |
|---|---|
| "实体死亡时减计数" | 无原生回调 → `testfor` 判空 / 死亡代理盔甲架 / 玩家击杀增量 |
| "检测选择器是否匹配" | `execute if @e` 是 1.13+ → 用 `testfor`（且 `testfor` 只给 0/1，不给数量） |
| "把命令结果存进计分板" | `execute store` 是 1.17+ → 用 `stats entity ... set SuccessCount` |
| "函数提前返回" | 无 `return` → 嵌套守卫函数 |
| "读取命令执行数量" | `stats entity ... set AffectedEntities`（1.12 有限支持，且有时序陷阱） |

## 6. 建议的追踪顺序（实操 checklist）

```
0. 先把命令方块按变体分桶：
   repeating → 传感器（每 tick 自跑，不需要电源，auto 无意义）
   chain     → 执行体（被链触发）
   impulse   → 动作头（需要外部触发，是 R2 的唯一适用对象）
1. 列出所有 impulse 动作头
2. 对每个 impulse：
   a. 命令是 execute @a[box] ?            → 玩家触发，记录 box
   b. 有 chain 边指向它 ?                 → chain 触发，回溯链头
   c. 有 comparator 边指向它 ?            → 比较器供电（延迟 2 tick），
                                             回溯比较器**后方**被读取的方块（可隔导体块）
   d. 6 面有电源 ?                        → 直接供电，记录延迟
   e. 6 面邻接的**实心方块**本身被直接供电 ? → 二级传导得电（记录源头与延迟）
   f. 相邻有红石粉 ?                      → BFS 粉网络，看是否接到电源
   g. 都不成立                             → needs_manual_trace，考虑升级作用域
3. 对每个 repeating 传感器：
   a. 它供给哪个比较器？                  → 找到"后读"它的那个比较器
   b. 该比较器输出给谁？                  → 直接点亮动作头 = 正向触发
   c. 该比较器输出后面是否接了
      石砖 + 火把 + 动作头 ?              → 反相触发（传感器失败才动作）
4. 对所有 setblock 红石类命令：
   a. 记下目标坐标，扫描 26 邻域的受电方块   → 交接边（延迟 1 tick）
   b. 查同坐标是否有移除命令                → R4
   c. 判定 plumbing / gameplay              → 迁移决策
   d. 查这个 setblock 的相对形式
      （`setblock ~1 ~ ~ redstone_block`）   → 落点在执行点旁边，也要算交接边
5. 走 chain 图，检查是否有环                → R5（三色 DFS）
6. 用 TileEntity 的 LastExecution 做时序自检：
   同一 lane 的 chain 块 LastExecution 应完全相同；
   交接点两侧应相差 1 tick
7. 跑全部审计规则
```

> 第 6 步是**免费的运行时证据**：`LastExecution` 记录每个命令方块上次执行的 tick。
> 用它可以把静态推导的时序和真实运行对齐——交接是否真是 1 tick、
> 比较器是否真是 2 tick、某条 lane 到底有没有被触发过，一目了然。
> 静态分析拿不准的地方，先看这个字段。
